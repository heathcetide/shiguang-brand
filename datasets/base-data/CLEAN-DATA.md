# 三份业务数据与初始化数据

本目录是应用接入用 JSON 契约，尚未写入现有数据库。

- ingredients.json：目录 ID、名称、可采用别名、分类、状态、来源。营养未知为 null。
- recipes.json：菜谱 ID、名称、原文/结构化用量、步骤、来源、食材与厨具引用及能力标志。
- kitchenware.json：厨具 ID、规范名、已筛选精确别名、分类、来源；没有自动替代关系。
- initial-data.json：管理员配置、演示账户、帖子、评论、库存和收藏，全部使用稳定逻辑 ID。

## 已完成的清洗

名称执行 Unicode NFKC 和首尾空格清理。原始食材别名仍有语义问题，先保留在审核清单；
同名不同来源 ID 不合并。仅对厨具精确别名白名单进行启用，其余继续审核。
菜谱仅将完整的“数字＋g/克/kg/千克/ml/毫升”识别为数量，kg 换算为 g；
范围、每份公式、“适量”和个/勺均保留原文，不猜重量。食材名称唯一命中时保存目录引用，
未命中或有多个同名 ID 时保持 null。原始计算区、操作区与注意事项保留用于复核。

## 可用范围

447 条食材可供目录检索，241 个厨具可供目录选择，341 条菜谱记录可供阅读/审核。
341 是 321 篇来源文档加 20 道项目草稿，不能视为去重菜式数量。
20 道项目草稿有明确份数、用量和完整引用，has_structured_amounts=true；
来源菜谱需要逐篇审核，has_structured_amounts=false，缺失值不得当零。
can_display=true 表示可展示资料，不等于已通过发布或烹饪安全审核。
所有 automatic_inventory_write_allowed=false，防止未审核来源造成错误库存扣减。
不声称这批数据已通过实做验证或营养核验。

## 账户与社区初始化

按用户要求，所有环境默认包含管理员配置、示例账户和帖子，environment=all。示例数据仍标记 is_demo=true，角色保持普通用户。
管理员密码从 DDD_BOOTSTRAP_ADMIN_PASSWORD 获取；三个演示账户分别从
DDD_DEMO_PASSWORD_1/2/3 获取。包内没有密码、密码哈希、邮箱、手机或令牌。
执行导入时必须校验密码强度、使用服务端 bcrypt，并在账号首次登录要求改密；
已有同名账户应跳过且报告，不能重设其密码或提升其角色。
帖子共 100 条，围绕 20 道关联菜谱分为采购、备料、操作安排、份量和交流五类内容，正文不加“【演示内容】”前缀。
底层 is_demo 标记保留，点赞浏览量为零；6 条评论和6 条收藏保持原规模。
库存到期日期由导入时间加 expires_in_days 计算，只用于演示；不作为保质期建议。
导入顺序为账户 → 三份基础数据 → 帖子 → 评论/库存/收藏。
导入器应持久化逻辑 ID 到数据库 ID 的映射，事务导入，重复运行跳过已有种子，
不得按名称覆盖用户数据。指标必须排除 is_demo；现有系统尚需接入这些字段。

## 当前数据库适配缺口

现有 ingredients_library.calories_100g 为 NOT NULL，不能直接装载未知热量。
接入前应允许营养未知，或使用独立目录层，不能为通过约束写入 0。
recipes 当前存储结构需要映射新 ID 和质量标志；账户、帖子等整数外键也需要 ID 映射。
因此本次完成数据文件及校验，未连接或修改实际数据库，也未创建真实可登录账号。

从仓库根目录校验导出目录：

```powershell
python datasets/base-data/clean_data.py .cache/base-data-releases/clean-0.1.0-rc.7
```
