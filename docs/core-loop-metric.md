# 每周核心闭环统计口径（#186）

版本：`weekly-core-loop-v1`。统计时区：`Asia/Shanghai`，自然周从当地周一 00:00 开始，到下周一 00:00 结束（不含）。通过 IANA 时区规则换算 UTC，不依赖服务器本地时区。查询可传入周内任一天。

## 有效闭环

同一持久化制作记录必须具备以下关联证据：

1. 已分类为真实用户，属于目标环境，使用独立于登录密钥的稳定最小用户标识。
2. 当前用户的推荐/选择来源与制作菜谱一致，选择时确实匹配了具体库存批次。
3. 至少一个被匹配的库存批次有更早的用户确认入库证据，且属于该用户或该次制作的同一家庭。
4. 制作事务确实扣减该批次。前后数量和扣减量一致，数量未知、只有客户端点击或没有持久化扣减的记录不计入。
5. 制作者本人有与该制作关联、已保存且未撤销/删除的实际摄入记录。单纯做完、家人吃了或保存待吃成品均不足以给制作者计数。

按首次仍然有效的摄入记录的**服务端提交时间**归周，不使用客户端回填的饮食日期。入库、选菜和制作可以发生在更早的周。同一批制作跨周分次食用仍只算一次闭环；同一用户同周多次闭环计一人，闭环次数另列。

撤销/删除首次摄入后，重算时选择下一条仍有效的实际摄入；因此可能移到另一周或完全不再计入。账号删除遵循现有删除策略，后续不保留该账号的逐条证据或纳入重算。

## 缺失、零值与覆盖

- `not_collected`：未配置目标环境/采集起点，或该周尚未进入采集范围；人数和闭环数是 null。
- `partial`：采集从周中开始，或有可能归属该周但来源证据不足的摄入；总人数和总闭环数是 null，另列已核实下限 `verifiedUsers` / `verifiedLoops` 与待核对条目数。
- `in_progress`：当前周尚未结束，显示截至查询时刻的实际人数。
- `complete`：完整覆盖已结束的周，无未判定证据。此时无有效记录才可以显示真实 0。

1–29 人显示实际人数及小样本标识，不输出百分比或因果结论。逐条核对只需制作 ID、稳定用户标识、状态和原因，不复制食物名称、营养/健康信息或原始对话。

## 查询、配置与当前覆盖

管理员页面为 `/admin/core-loops`。受管理员认证保护的接口：

- `GET /api/v1/admin/core-loops?date=2026-09-12&details=1`：从同一数据库快照重算该周；明细最多 200 条，汇总不截断。
- `GET/PUT /api/v1/admin/core-loops/settings`：读取或设置启停状态，写入需要当前 `version`。
- `GET/PUT /api/v1/admin/core-loops/actors/:userId`：读取/设置 `unknown/real/test/demo/automation` 分类，写入需要当前 `version`（首次为 0），变更和审计在同一事务提交。

先在服务端配置独立的 `CORE_LOOP_ENVIRONMENT`（例如 staging），再在管理端启用。默认不采集；第一次启用记录服务端采集起点。配置同时绑定环境，数据库恢复到另一个环境后不会沿用旧覆盖范围，必须重新启用。不会用 NODE_ENV 推断 staging，也不会自动把普通注册用户分类为真实内测用户。

稳定用户标识使用 `user:<数据库用户主键>`，仅出现在管理员核对接口。主键在账号存续期间稳定，不依赖 JWT 或日志 HMAC 密钥；删除账号时分类行级联删除。原始业务事实遵循现有账号删除策略。

当前可核实的真实链路是**个人确认入库→库存推荐→加入队列→制作扣减→本人实际摄入**。入库证据包括手动创建、购物清单确认导入，以及统一入库接口逐项确认的图片/小票/条码/最近记录；识别来源不能单独证明确认，必须有服务端保存的 manual acceptance。自动接受的识别结果和缺少确认标记的旧 AI 入库不计为已确认。购物导入在同一事务写入创建日志，幂等重试不新增日志。来源来自服务端推荐快照和队列；库存数量与同次制作的持久化变更日志精确对账。SQLite/PostgreSQL 均在一致数据库快照中读取，时间比较统一为秒级（兼容 SQLite 的提交时间精度）。汇总不依赖单独埋点写入；埋点失败后的重新查询仍能从业务事实恢复结果。

历史旧式完成记录、未保存环境的制作、其他尚无确认日志的入库来源与共餐来源证据尚不完整时保留为未知，不通过用户/时间猜测关联，也不会算成确定零。制作请求、扣减快照和共餐安排不能代替选择及入库确认，家庭证据采集仍未完整接通。**这些路径仍需补齐，#186 尚未全部完成。**家庭来源不足只对实际吃过的制作者保留待核对项，不给所有成员记一次闭环。

已验证：固定数据的跨年/跨周、早先周入库、同用户去重、纠错与 0/1/30 人；SQLite 真实 HTTP 的权限隔离、入库到摄入、重试、分类排除和撤销；PostgreSQL 对应业务链、并发分类 CAS、审计与重算。两种数据库均模拟埋点写入失败。管理端在隔离本地库验证未采集、周中启用的已核实下限与分类读取；这些是合成验收数据，不是真实内测指标。
