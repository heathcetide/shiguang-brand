## 第二轮第一组：正式待吃餐次份量记录（2026-09-13）

新增 SQLite 82 / PostgreSQL 0024 的 prepared_meal_allocations 表，记录餐单、目标餐次、实际批次、安排及未结清份量、状态、版本和原始来源。批次沿用现有制作来源的队列与餐单项身份。活动草案的旧安排使用确定性身份迁入；缺失/跨账号批次、旧版本、手动保留或超额安排标记 conflict，保留原草案和来源，不选择性覆盖。结构本身损坏会使迁移失败并整体回滚，需核对原数据后重跑。

新激活安排、推荐预算和 Agent 上下文读取正式记录。食用/丢弃在同一事务中结清指定餐次份量；延期只改该安排；撤销误记食用同时恢复原安排，后续已修改或取消则拒绝。取消单项安排或整个餐单只释放对应记录，不改变实际剩余量。多个安排必须选择对象；allocation_id:null 明确使用未安排份量，不借用别的餐次。

接口向后兼容新增 allocation_id / allocation_version、release_allocation 与响应 allocations；旧客户端在唯一安排时可继续操作，多个安排时返回确认要求。客户端展示并选择日期/餐次，保留原操作身份重试；同批次版本下也可刷新安排，防止取消后仍显示旧占用。PostgreSQL 各入口统一先取得餐单锁，再取得待吃餐与行锁。

新表 SQL 集中在专用 SQLite/PostgreSQL 仓储，未在路由、服务或客户端增加直接 SQLite 访问。SQLite 基线只新增 mealAllocations/sqliteRepository.ts 的 5 处类型/仓储访问，餐单仓储移除旧草案查询后计数减少 1；配套双库实现与集成测试随本次功能提交，不放宽通用检查规则。
