# 拾味日常 · 数据闭环说明（当前版）

本文面向 **研发与验收**：说明数据如何流转、功能如何闭环，以及后台该管什么。普通用户请优先阅读带截图的 [用户指南](../getting-started.md)。营养与 AI 输出仅供日常参考，不能替代医疗建议。

配套入口：[用户指南](../getting-started.md) · [操作手册总览](README.md) · [文档索引](../README.md) · [运维部署](../operations.md)

---

## 1. 产品定位（先分清两条线）

| 主线 | 目标 | 用户感知 |
| --- | --- | --- |
| **营养主闭环** | 今天吃了什么 → 对照目标 → 安排下一餐 | 首页热量/宏量环、饮食记录、推荐、健康档案 |
| **厨房支撑闭环** | 家里有什么 → 能做什么 → 做完扣库存 → 记摄入 | 库存、采购、烹饪队列、厨具、成品待吃 |

厨具、库存不是替代营养主线，而是让「推荐」和「做饭」更贴真实厨房。

## 2. 数据闭环总览

```text
健康档案（目标热量/蛋白/碳水/脂肪 + 过敏忌口）
        │
        ▼
饮食记录（手动 / 识图 / 烹饪完成写入）──► 按「上海日历日」汇总今日摄入
        │                                      │
        │                                      ▼
        │                         推荐打分（目标 − 今日已摄入 + 库存可做 + 忌口）
        │                                      │
        ▼                                      ▼
首页宏量环 / 营养分析 ◄─────────────── 首页下一餐教练 / 推荐 / 助手
        ▲
        │
库存食材 ──► 采购补缺 ──► 烹饪队列 ──► 做饭扣减 ──► 实际食用写入饮食记录
厨具目录/资产 ──────────────────────────┘（影响可做菜与能力匹配）
```

**日期口径**：客户端与服务端统一用 **Asia/Shanghai** 的「应用日」键（`YYYY-MM-DD`）汇总今日摄入与推荐，避免跨时区把「今天」算错。

**趋势 API**：`GET /api/v1/diet-records/summary?days=7|30` 返回每日宏量桶、目标、达成率与今日剩余额度；「我的 → 营养分析」消费该接口。

**持久化**：业务数据在 Go API（`:9090`）的数据库（本地可 SQLite；当前环境可切 MySQL）。菜谱/食材图片等媒体走对象存储 CDN；管理端与客户端都读同一套 API。

## 3. 客户端：最短上手路径

1. **注册 / 登录** → 邮箱 + 密码。  
2. **健康档案**：设目标热量，建议同时补蛋白/碳水/脂肪与过敏/忌口。  
3. **记一餐**：`饮食记录` 手动录入，或识图预填后核对再保存。  
4. **回首页**：看热量环、蛋白/碳水/脂肪进度环与剩余额度。  
5. **安排下一顿**：首页「下一餐教练」/ 推荐 / 搜索 / 拾味助手；优先用库存可做菜。  
6. **回顾**：`我的 → 营养分析` 查看近 7/30 日趋势与目标达成。  
7. （可选）**厨房闭环**：入库 → 采购 → 加入烹饪队列 → 做饭完成并勾选实际食用 → 再次看首页环。

### 3.1 各 Tab 职责

| Tab | 做什么 | 闭环角色 |
| --- | --- | --- |
| 首页 | 今日宏量环、下一餐教练、推荐、库存/采购摘要、助手入口 | 营养结果面 + 下一餐入口 |
| 资产 | 食材库存、厨具 | 厨房能力输入 |
| 社区 | 动态/关注 | 不参与营养合计 |
| 我的 | 健康目标、营养分析、餐单/烹饪、设置 | 目标与回顾 |

### 3.2 饮食记录要点

- 有依据再填热量与蛋白/碳水/脂肪；没有就留空（会出现「营养待补全」，**不要编造**）。  
- 多份量时务必带上每份营养，服务端会按份量落库。  
- 同一操作可带幂等键，避免重复提交产生双份记录。

### 3.3 烹饪完成如何进闭环

做饭完成且勾选「实际食用」时，服务端在同一事务路径写入：烹饪完成状态 +（可选）成品 + **饮食记录（含宏量）**。成功后首页「今日摄入」应立即可见变化。

## 4. 后台管理员：管什么、怎么用

地址示例：`http://localhost:5173`（开发代理到 Go `:9090`）。

| 模块 | 作用 | 与闭环关系 |
| --- | --- | --- |
| 工作台 | 运营概览 | 观测 |
| 食材 / 菜谱 | 目录质量、营养字段、图片 | 推荐与记餐依据 |
| **厨具** | 官方目录 + 用户资产 + 能力条件 | 可做菜 / 烹饪能力匹配 |
| 用户 | 账号与停用 | 安全 |
| 社区 / 通知 | 内容与触达 | 运营 |
| AI 配置 / 用量 / 会话 | 模型与成本 | 识图、助手、语音 |
| 媒体清理等 | 存储卫生 | 运维 |

### 4.1 厨具页（`/admin/kitchenware`）

- **官方目录**：标准厨具名、别名、分类、图片、能力条件；影响用户映射与推荐侧能力。  
- **用户资产**：查看用户家中厨具状态（常用/需保养等），可调整状态或移入回收站。  
- 筛选与分页走查询参数；改目录后客户端侧能力画像会间接受益。

## 5. 闭环验收清单（建议自测）

1. 健康档案：热量 2000、蛋白 90、碳水 220、脂肪 60（示例）。  
2. 新建饮食记录：热量 500、蛋白 30、碳水 40、脂肪 15，日期为「今天」（上海日）。  
3. 首页：热量环约 500/2000；蛋白/碳水/脂肪环显示进度；剩余热量约 1500。  
4. 首页「下一餐教练」与推荐：更贴合剩余额度的菜谱应相对更靠前。  
5. 记餐成功弹窗可进「下一餐教练」；「我的 → 营养分析」能看到近 7/30 日柱状趋势与达成率。  
6. 健康档案填写重度海鲜过敏或「无海鲜」限制后，含虾蟹的推荐应被排除或显著降权。  
7. 烹饪完成并勾选食用：再产生一条饮食记录，环继续累加；刷新后数据仍在。  
8. 换一天的日期筛选：只看到对应日的记录，不串日。

失败时优先查：是否连错库（SQLite vs MySQL）、日期是否被本地时区偏移、饮食记录是否缺少宏量字段。

## 6. 当前边界（诚实说明）

- **过敏 / 忌口过滤**：推荐打分对健康档案过敏原做匹配——`severe` 直接排除，`mild/moderate` 降权；`dietary_restrictions`（如无麸质/无海鲜）按中度忌口参与过滤；「素食/纯素」会硬过滤动物原料菜谱。别名覆盖常见标签，这是**日常辅助**，不是医疗级屏蔽，仍请人工确认菜谱原料。  
- **营养分析**：首页有今日热量 + 三大宏量进度环；「营养分析」页提供 7/30 日趋势、达成率与今日剩余额度（`/api/v1/diet-records/summary`）。  
- 识图结果必须人工确认后再入库/记餐。  
- 饮食记录保存成功后，若日期为上海「今天」，会提示下一餐候选并可跳转教练（失败时静默忽略）。  
- 社区、部分通知/干预任务属于运营侧，不计入营养合计。

## 7. 本地开发快速启动

```bash
# 仓库根目录
bun run dev:server   # Go API :9090
bun run dev:client   # Expo
bun run dev:admin    # 管理端 :5173
```

数据库：默认可读 `server/configs/config.yaml`；本地密钥与 MySQL DSN 放在 **gitignore** 的 `server/configs/config.local.yaml`。
