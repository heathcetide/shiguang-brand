# 食光烙记未来功能排期清单

> 本文档用于统一收集整个项目未来期望实现的产品功能、技术范围、实施阶段与验收要求。各项功能按 `F-1`、`F-2`、`F-3` 等编号持续追加；在收到对应功能“开始实现”的明确指令前，不修改相关业务代码。

## F-1：独立社区帖子，可选嵌入菜谱卡片

- 状态：已有单份可选菜谱卡片实现；多菜谱、正文段落间自由插入等扩展尚未确认，不视为已排期需求。帖子详情顶栏中的“暂无完整菜谱”占位入口保持移除。
- 类型：产品功能 / 社区帖子 / 食谱关联 / 正文链接卡片
- 优先级：待统一排序
- 记录日期：2026-08-15；现状校正：2026-10-20（按当前代码核对，不代表已完成实机验收）
- 目标端：Android APK 实机、Web、Express.js 服务端
- 背景：帖子详情顶栏此前固定显示“暂无完整菜谱”，但普通帖子并没有关联食谱，该入口点击后也只能提示“暂不能开启烹饪”。这一设计会占用顶栏空间并让用户误以为当前帖子具备菜谱能力，因此现阶段已移除。
- 产品方向：帖子是独立的社区内容，不要求每篇帖子强关联菜谱。作者可以只发布文字或图片，也可以选择嵌入菜谱卡片。完整菜谱入口不放在帖子顶栏；仅当关联菜谱有效且可公开访问时才展示卡片，未关联时不展示菜谱提示或占位状态。
- 当前数据现状：`community_posts.linked_recipe_id` 已存在且可空；发帖校验允许省略该字段或传 `null`，传值时要求正整数。创建服务与 SQLite/PostgreSQL 仓储均支持普通帖子，并校验所选菜谱公开状态。接口及客户端类型已有 `linked_recipe` 摘要和 `linked_recipe_unavailable` 状态。基础数据导入包使用源字段 `recipe_id`，导入时映射到 `linked_recipe_id`；缺失或 `null` 表示不关联，显式无效引用仍报错，不改写已有帖子或冻结数据包。
- 设计原则：食谱关联应使用结构化数据保存，不依赖识别正文中的普通 URL、特殊文字或约定标签。正文卡片是结构化关联的展示结果，不应通过解析用户自由输入内容来猜测目标食谱。
- 期望交互：用户发布动态时可主动选择“关联菜谱”；选择完成后，发布页显示可预览、可更换、可移除的关联菜谱摘要。帖子发布成功后，详情页在正文内容与标签之后展示“这篇动态关联了完整菜谱”卡片，包含封面、菜谱名称、关键摘要和“查看完整菜谱”操作。
- 展示位置：关联菜谱卡片属于帖子正文内容的一部分，放在正文文字/图片/标签之后、发布时间与评论区域之前；不得重新放回帖子顶栏，也不得在无关联时显示“暂无完整菜谱”。
- 跳转行为：点击关联卡片或“查看完整菜谱”后，携带明确的菜谱 ID 进入对应食谱详情页；从食谱详情返回时，应回到原帖子详情并尽量保留滚动位置。
- 发布入口建议：在“写动态”页面增加非必填的“关联菜谱”入口。第一阶段允许从当前可公开访问的已发布菜谱中选择；是否优先展示用户投稿、收藏或家庭食谱，需结合后续个人/家庭库方案统一确认。
- 权限与有效性：服务端必须验证 `linked_recipe_id` 对应的食谱真实存在且允许公开访问，不能只信任客户端传值。待审核、已拒绝、已下架、已删除或无权限访问的食谱不得建立新的公开关联。
- 历史兼容：现有帖子默认没有关联菜谱，数据库迁移后仍应正常读取和展示；不得要求为旧帖子补写无意义的默认菜谱 ID。
- 失效处理：帖子关联的食谱后续下架、删除或转为不可公开时，帖子详情应自动隐藏关联卡片或展示明确的不可用状态，不得跳转到空白页面、错误页面或其他食谱。

### 当前实现与代码依据

- `server/src/validation/schemas.ts`、`server/src/modules/community/service.ts`：文字、图片、可选菜谱不要求同时存在；无菜谱帖子仍可发布。
- `server/src/modules/community/{sqliteRepository,postgresRepository}.ts`：新关联只接受未删除、已批准且不处于 `needs_review` 的菜谱；读取时也过滤失效关联。
- `client/screens/post-create/index.tsx`：已有公开菜谱选择器和选中摘要，支持重新选择及移除；每篇帖子当前最多关联一份，未选时提交 `null`。
- `client/screens/post-detail/index.tsx`、`client/screens/community/index.tsx`、`client/components/LinkedRecipeCard.tsx`：详情及信息流已有可点击卡片；详情卡片目前位于正文文字之后、分类标签之前。无有效摘要时不渲染卡片，也不显示“暂无完整菜谱”。
- 单份卡片不等于富文本编辑器：目前不能在正文任意段落间自由插入卡片，也不能嵌入多份菜谱。此类扩展需另行确认，不能从“可以嵌入菜谱”推导为强制关联或自动扩展范围。

### 原始分阶段方案（历史设计与后续核对清单）

以下保留原方案供核对，不是“全部未实现”的任务单，也不代表全部交互及 Android/Web 验收已经完成。实际已实现范围以上述代码现状为准；差异与扩展需先确认再排期。

#### 阶段一：数据模型与接口

- 为 `community_posts` 增加可空的 `linked_recipe_id`，并建立指向 `recipes` 的外键关系；删除食谱时采用 `SET NULL` 或等价的安全失效策略。
- 同步更新 SQLite 迁移、共享数据库 Schema、服务端类型与索引；评估是否需要为 `linked_recipe_id` 建立查询索引。
- 扩展发帖请求校验，使 `linked_recipe_id` 只能是正整数或 `null`，并在创建帖子前校验食谱的存在状态与公开状态。
- 扩展帖子列表及详情接口，返回稳定的结构化关联摘要，例如 `linked_recipe: { id, title, image_url, cook_time, calories }`；避免客户端仅拿到 ID 后额外发起不必要请求。
- 为非法 ID、不可见食谱、食谱删除及旧帖子兼容补充服务端测试。

#### 阶段二：发帖时关联菜谱

- 在“写动态”页面增加“关联菜谱（可选）”入口，并提供菜谱选择界面。
- 支持搜索或浏览候选菜谱；候选数据应只包含当前允许公开关联的食谱。
- 选中后在发布页显示菜谱摘要，支持查看、更换和移除；移除后发布普通帖子。
- 发布请求携带结构化 `linked_recipe_id`，提交失败时保留用户已填写的正文、图片与菜谱选择，避免内容丢失。
- 第一阶段每篇帖子最多关联一份完整菜谱；多菜谱关联不纳入本期，避免正文卡片和数据关系过早复杂化。

#### 阶段三：帖子正文关联卡片

- 扩展帖子详情客户端类型，读取接口返回的 `linked_recipe`。
- 仅在 `linked_recipe` 有效时渲染正文关联卡片；普通帖子保持当前简洁布局。
- 卡片采用独立、可识别但不过度抢占正文视觉层级的样式，明确标注“关联菜谱”或“查看完整菜谱”，不使用“开始烹饪”等会跨越当前流程的文案。
- 点击卡片进入现有食谱详情路由，并验证 Android、Web 的返回行为与滚动状态。
- 加载失败时不得阻塞帖子正文；关联摘要缺失或失效时应安全降级为不显示卡片。

#### 阶段四：信息流提示与后续扩展

- 评估是否在社区信息流卡片上增加轻量的“含完整菜谱”标识，帮助用户在进入详情前识别内容类型；该标识不得替代正文关联卡片。
- 评估作者是否可以在帖子发布后编辑、替换或解除菜谱关联，以及变更是否需要审核记录。
- 后续如实现富文本正文，可进一步支持在正文段落间插入菜谱引用；该能力应复用同一结构化关联机制，不通过解析自由文本链接实现。
- 多菜谱、个人/家庭私有菜谱分享、菜谱快照及审核联动均作为后续独立需求，不纳入第一期。

### 验收标准

- 未关联菜谱的帖子详情不显示任何“暂无完整菜谱”、禁用按钮或菜谱占位区域。
- 已关联且可公开访问的菜谱，在帖子正文区域稳定显示关联卡片，卡片信息与目标食谱一致。
- 点击关联卡片能够进入正确的食谱详情，返回后仍处于原帖子上下文。
- 客户端不能通过伪造 `linked_recipe_id` 关联不存在、未公开或无权访问的食谱。
- 食谱下架或删除后，既有帖子不会产生错误跳转，且普通正文、图片、点赞和评论功能不受影响。
- 不带 `linked_recipe_id` 的旧版本客户端仍能正常发布普通帖子；迁移前的历史帖子仍能正常读取。
- Android APK 与 Web 均完成发布、查看、跳转、返回、失效降级和错误重试测试。
- 帖子顶栏继续只承担作者信息、关注与分享等页面级操作，不重新加入菜谱状态按钮。

### 待确认事项

- 候选菜谱范围：全部官方公开食谱、用户本人投稿食谱、已收藏食谱，还是个人/家庭库中的可分享食谱。
- 投稿中或待审核的菜谱是否允许作者在仅自己可见的帖子预览中关联。
- 帖子审核机制接入后，关联菜谱是否影响审核规则，菜谱变更后是否需要重新审核帖子。
- 食谱删除时采用直接隐藏卡片、显示“原菜谱已下架”，还是保留发布时的只读摘要快照。
- 社区信息流是否需要展示“含完整菜谱”标识，以及该标识对排序或推荐策略是否产生影响。

### 风险

- 如果仅保存正文 URL 而不建立结构化关联，将难以可靠处理权限、下架、删除、路由变更和数据统计。
- 如果允许关联私有或待审核食谱，可能通过社区帖子泄露原本不可公开的内容。
- 如果接口只返回 `linked_recipe_id`，详情页可能产生额外请求、加载闪烁和失效状态不一致；建议直接返回受控摘要。
- 如果食谱删除策略未提前确定，历史帖子可能出现死链接或正文语义缺失。
- 如果在帖子顶栏、信息流和正文同时放置强入口，容易再次造成页面操作层级混乱；第一期应以正文关联卡片为唯一主要入口。
