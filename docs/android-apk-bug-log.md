## B-4：发表评论时看不到评论输入框

- 状态：已按真实键盘坐标重构定位，移除固定延时与重复避让，待 Android APK 多输入法实机回归
- 类型：交互 / 键盘适配 / 评论输入
- 优先级：P1（总顺序 1）
- 记录日期：2026-08-13
- 补充记录日期：2026-08-14
- 测试端：Android APK 实机
- 现象：用户在帖子详情页点击底部评论输入入口后，评论框先于系统输入法弹出；输入法随后出现且页面内容被半透明遮罩覆盖，但评论输入框及发送操作区没有稳定地停靠在输入法上方。用户无法看到当前输入内容，也无法正常找到提交评论的操作入口。
- 期望：键盘弹出后，评论输入框和发送按钮应始终位于键盘上方的可见区域；输入内容应可见，且可正常取消或提交评论。
- 复现路径：打开 Android APK → 进入社区 → 打开帖子详情 → 点击底部“说点什么吧，与食友交流...”评论入口。
- 复现频率：当前截图所示场景可复现；精确频率待确认。
- 附件：
  - Android 实机截图：`codex-clipboard-89959c26-3c06-4459-81f2-259614437e91.jpg`
- 当前实现线索：现有流程先显示评论 `Modal`，再通过约 120ms 的固定延时聚焦输入框，由输入框触发系统键盘；弹层使用 `slide` 动画，并依赖 `KeyboardAvoidingView` 在 Android 上二次调整高度。固定延时不代表键盘已经完成显示，不同输入法、设备性能和厂商动画时长都可能造成时序与位置不一致。
- 修改思路：点击评论入口后先让输入控件获取焦点并请求系统键盘；Android 监听 `keyboardDidShow`，以事件返回的实际键盘坐标或高度作为评论框定位依据，确认键盘可见后再展示评论框，或让评论框与键盘联动动画并始终贴合键盘上沿。不得仅通过增加固定延时规避问题。
- 布局约束：无论系统采用窗口 `resize` 还是弹层独立窗口，评论框底部位置都应由当前可视区域与键盘实际边界计算；需要避免页面外层与弹层内层的多重键盘避让重复生效，并正确处理底部安全区、键盘切换、键盘收起和弹层关闭。
- 验证重点：覆盖首次打开、连续打开关闭、切换不同输入法、切换表情/数字键盘、添加评论图片、长文本输入和返回键收起键盘；确认评论框不闪跳、不被遮挡，发送与取消按钮始终可见可点击。

## B-36：APK 缺少统一、快速的数据缓存与预缓存机制

- 状态：新发现，已完成现状核查，未修复
- 类型：性能 / 缓存架构 / 预缓存 / 离线体验
- 优先级：待统一排序
- 记录日期：2026-08-24
- 测试端：Android APK 实机
- 现象：APK 实机使用时，页面数据缺少快速复用能力，进入或返回页面后仍需要等待接口重新加载；应用也没有在合适的生命周期提前准备首页及高频页面所需数据，导致冷启动、切换页面和弱网场景的等待感明显。
- 当前实现核查：通用 `requestJson` 请求层只对写操作做了并发去重，没有 GET 请求去重、内存缓存、持久化响应缓存、TTL、过期重验证或失败回退。首页每次聚焦会并行重新请求菜谱、社区、库存、当日饮食和健康数据，并持续显示加载状态直到请求完成。当前仅库存页的默认菜谱和库存快照等少量数据使用 AsyncStorage 做零散离线兜底，且没有统一的版本、有效期及失效策略。
- 图片现状：`RecipeCover` 已通过 `expo-image` 启用 `memory-disk` 缓存，但社区图片、头像、饮食记录图片等大量远程图片仍使用 React Native `Image`，没有统一的磁盘缓存和预取策略；首屏图片也未根据即将展示的内容提前预取。
- 期望：建立统一且可观测的多层缓存机制。页面应优先快速展示可用的内存或本地快照，再在后台刷新；首次安装联网成功后应缓存必要数据，后续启动和弱网时仍能快速展示最近一次有效内容。应用启动、登录完成或用户即将进入高频页面时，应按优先级预缓存首页、社区首屏、常用菜谱及其首屏图片，不能无边界地下载全部数据。
- 数据一致性要求：缓存必须按公共数据与用户私有数据分区，私有缓存按用户隔离；新增、编辑、删除、点赞、收藏、库存变更和退出登录后应精确失效或更新相关缓存。手动下拉刷新必须能够绕过新鲜缓存请求服务端；过期数据、接口结构升级和损坏缓存应安全降级，不得造成跨账号数据展示或长期显示旧数据。
- 性能与容量要求：需要分别定义内存缓存、API 响应缓存和图片/文件缓存的容量、TTL、淘汰规则及预缓存预算；预缓存应考虑移动网络、低电量和存储空间，避免增加首启阻塞、流量消耗或后台压力。“清理本地缓存”应覆盖新增的可清理缓存并继续正确显示清理前后大小，但不得误删登录凭证或用户明确保存的数据。
- 建议验收指标：记录冷启动到首页可用内容、二次启动到缓存内容、主要 Tab 二次进入、弱网和完全离线等场景的可见时间；验证相同请求并发合并、缓存命中、后台重验证、手动强刷、写后失效、缓存过期、应用升级、账号切换和清除缓存。具体时间与容量阈值需在实现前结合 APK 实机基线确定。
- 复现路径：打开 Android APK → 等待首页加载 → 进入其他主要页面后返回或重复切换 → 观察数据再次等待请求；在弱网或断网环境重新启动并进入首页、社区、食谱等页面 → 观察缺少可立即展示的历史快照和预缓存内容。
- 复现频率：当前实机体验已发现；不同网络、设备性能和页面的具体差异待专项测量。
- 附件：本条暂无截图或性能录屏，依据 Android APK 实机使用反馈与当前客户端代码核查记录。
- 关联问题：B-15 已解决“缓存大小展示与清理反馈”，本条关注缓存本身的统一架构、命中速度、预缓存、数据一致性与离线体验，不重复 B-15。
- 备注：根据本清单约定，本次仅记录反馈并核查现状，不开始修改业务代码。正式实现前应先采集 APK 性能基线，再分阶段接入数据缓存、首屏预缓存和图片缓存，避免一次性扩大缓存范围后难以验证一致性。
